# JRHOF Google Workspace Migration Plan

**Status:** Planning only — no production migration authorized  
**Date:** 2026-09-18  
**Goal:** Make Google Workspace the primary human productivity platform for JR & Associates while preserving the website, Cloudflare, GitHub, Stripe, and other purpose-built systems that already work well.

## Why this direction

JRHOF is a small nonprofit with volunteer/board operations. The productivity platform should be easy for nontechnical board members to use, inexpensive to operate, and simple to hand off.

Google Workspace for Nonprofits currently provides a no-cost nonprofit edition with Gmail, Calendar, Meet, Shared drives, centralized administration, 100 TB pooled storage, and Gemini with enterprise-grade data protections.

Official reference: https://support.google.com/nonprofits/answer/2858465

This migration does **not** imply moving the website, GitHub, Cloudflare, Stripe, analytics, or event application into Google Workspace.

## Target-state architecture

### Google Workspace — primary human collaboration

Use Google Workspace for:

- organizational email and aliases/groups
- shared calendars and board/event calendars
- Google Meet for board and committee meetings
- Shared drives for board, operations, events, finance/admin documents, approved media originals, and institutional records
- Docs, Sheets, Forms, and Slides
- lightweight board collaboration and volunteer handoff
- nonprofit AI capabilities where appropriate and approved

### GitHub — technical source of truth

Keep GitHub for:

- JRHOF website source
- architecture and technical decisions
- configuration and deployment documentation
- technical backlog/issues
- code review and change history

Board members should not need GitHub for ordinary nonprofit work.

### Cloudflare — web platform

Keep Cloudflare authoritative for:

- DNS
- website hosting/deployment
- R2 public media derivatives
- web security and access controls
- applicable Workers/D1 infrastructure

### Stripe — money and payments

Keep Stripe authoritative for payment processing and financial transaction records generated by Stripe.

### Microsoft 365 — migration source, then minimum justified footprint

Do not shut Microsoft down first.

Use the migration to determine what, if anything, should remain in Microsoft after:

- mail/calendar data is migrated and validated
- Teams-backed SharePoint files are migrated or intentionally retained
- OneDrive content is reviewed
- Teams communication/history retention needs are decided
- nonprofit licensing and account ownership are documented

The preferred end state is **Google-first**, with Microsoft retained only for a clearly documented reason.

## Current-state inventory required before migration

Use the working [Phase 0 inventory](JRHOF_GOOGLE_WORKSPACE_INVENTORY.md) to capture the current state before changing MX records or deleting licenses.

Create a simple inventory before changing MX records or deleting licenses.

### Identities

Record:

- active users
- admin accounts
- shared mailboxes
- distribution lists / Microsoft 365 groups
- aliases
- service/application accounts
- former users whose data must be retained
- Google accounts that already exist for the same people

### Email and calendars

Record:

- mailbox sizes
- shared mailboxes and delegates
- important aliases
- recurring board/event meetings
- shared calendars
- room/resource calendars, if any
- forwarding rules or automated mail flows

### Teams / SharePoint / OneDrive

For every Team and important SharePoint site, record:

- site/team name
- owner
- active members
- purpose
- approximate file volume
- whether content is still active
- destination Shared drive
- whether Teams chat/channel history needs archival treatment

Remember: standard Teams channel files are SharePoint content; private/shared channels may have their own SharePoint sites. Treat the Microsoft file inventory as a SharePoint/OneDrive migration, not merely a Teams migration.

### Applications and integrations

Identify anything using Microsoft identity or mail:

- website forms
- SMTP relays
- calendar integrations
- third-party apps
- automation
- sign-in-with-Microsoft dependencies
- board devices configured with Microsoft accounts

## Proposed Google information architecture

Start small. Do not recreate Microsoft sprawl inside Drive.

### Shared drives

Proposed initial drives:

1. **JRHOF Board & Governance**
   - agendas
   - minutes
   - policies
   - bylaws/governance
   - board working documents

2. **JRHOF Operations**
   - procedures
   - vendors
   - technology handoff material intended for nontechnical operators
   - volunteer/admin resources

3. **JRHOF Events**
   - banquet
   - golf tournament
   - event planning
   - approved working exports/reports

4. **JRHOF Finance & Administration**
   - finance/admin documents
   - contracts
   - insurance
   - state/nonprofit records
   - restricted to the appropriate board/officers

5. **JRHOF Media Originals**
   - approved original photos/programs/flyers
   - source archive for media that may later receive optimized public derivatives in R2

Do not put passwords, API secrets, private keys, or recovery codes in Shared drives.

## Migration approach

### Phase 0 — discovery and safety

- confirm Google for Nonprofits / Workspace status
- identify Google super administrators
- inventory Microsoft users, groups, mailboxes, calendars, SharePoint sites, Teams, and OneDrive
- export/document DNS and current mail records
- document Microsoft licensing and renewal dates
- identify retention/legal requirements
- decide which Microsoft content is intentionally *not* migrated
- create rollback/cutover owner

**No production changes in this phase.**

### Phase 1 — build the Google target

- normalize users and admin roles
- create Groups and aliases
- create Shared drives
- create calendar structure
- configure baseline MFA/security
- confirm Meet settings and test board-member joining experience
- validate external sharing defaults
- prepare destination permissions

Google Meet can include phone dial-in when the Workspace organization/admin configuration supports it. Validate JRHOF's actual edition/settings before promising a board call-in workflow.

Reference: https://support.google.com/meet/answer/9303069

### Phase 2 — pilot migration

Pilot with one or two noncritical accounts first.

Validate:

- mail
- labels/folder translation
- calendar events
- contacts
- permissions
- SharePoint/OneDrive file structure
- Google-native collaboration
- mobile access
- board-member usability

Do not use a migration success message as the only validation; compare source/target counts and spot-check critical records.

### Phase 3 — file migration

Map Microsoft content intentionally:

- SharePoint/Teams files → appropriate Shared drives
- OneDrive organizational material → Shared drives
- truly personal working files → user My Drive where appropriate

Avoid copying obsolete or duplicate content just because it exists.

Google's older Google Workspace Migrate path for SharePoint Online and OneDrive stopped receiving updates and bug fixes on September 15, 2026. Its Exchange Online path is also being retired starting October 2026. Use Google's current supported migration/import path at execution time rather than building this project around the aging workflow.

Migration reference:
https://support.google.com/workspacemigrate/answer/9275518

### Phase 4 — mail/calendar cutover

Only after pilots and file validation:

- lower DNS TTL ahead of cutover if needed
- run final/delta mail migration using the supported current Google tool
- update MX and mail-related DNS
- validate inbound/outbound mail
- validate SPF, DKIM, and DMARC
- validate calendar/Meet workflows
- validate aliases/groups
- keep Microsoft available during the defined rollback window

Do not cancel Microsoft licenses on cutover day.

### Phase 5 — board adoption

Keep the human change small:

- one short board orientation
- one-page “where things live” guide
- Meet joining instructions
- Shared drive navigation
- how to find board/event files
- who to contact when access is wrong

Success means board members can participate without learning GitHub, Cloudflare, or the website build stack.

### Phase 6 — Microsoft retirement decision

After a stable validation period, classify Microsoft components:

- **Retire**
- **Retain temporarily**
- **Retain long-term with documented reason**

Then:

- remove obsolete licenses
- disable unused accounts safely
- preserve required exports/records
- update architecture docs
- update account ownership/recovery documentation
- record the final platform decision in `docs/DECISIONS.md`

## What should not move just because Google becomes primary

Do not migrate these simply for platform consistency:

- GitHub repositories
- Cloudflare zones/Workers/R2/D1
- Stripe
- Google Analytics / Tag Manager / Ad Grants configuration
- technical configuration that belongs in Git
- public optimized media already correctly served from R2

The objective is a simpler **human productivity platform**, not a single-vendor architecture.

## Migration tooling note — September 2026

Before execution, re-check the official migration documentation. Do not copy an old runbook blindly.

## Definition of done

The migration is complete when:

- Google Workspace is the normal place board members use for email, meetings, calendars, and shared documents
- board members can find current files without TMCO intervention
- required Microsoft mail/files have been migrated or explicitly retained
- Microsoft dependencies are documented
- duplicate/outdated Microsoft services are retired
- DNS and email authentication are validated
- access is least-privilege
- architecture and handoff docs reflect reality
- no website/payment/Cloudflare capability was unnecessarily replatformed
